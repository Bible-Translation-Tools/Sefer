# 05 — Adopt the editor donor's proven core

Status: proposed. Prerequisites: [03](v2-03-engine-consumer-boundary.md), [04](v2-04-source-and-book-lifetime.md). Owns: Sefer's use of editor core; Onion owns USFM structure.

## Outcome and increments

1. Inventory the donor's current exported seam, property rulings, engine version, and host recipe. Its [latest handoff](../../../onion-2-spike/NEXT-STEPS-REMEDIATION-HANDOFF.md) records remediation completion; adopt the result rather than reimplementing its old defects.
2. Prove the smallest headless composition in Sefer: exact source → structural projection → resolved editor policy → one accepted/rejected edit. Choose vendored code versus package delivery explicitly and record provenance.
3. Mount that composition in Solid through a thin owner/disposal adapter. Preserve registry-based policy and shared ownership queries. Port behavior, not the React demo, diagnostic UI, or every harness.
4. Resolve remaining product-sensitive donor rulings before the associated gesture ships: range-merge behavior, settling direction, trusted surfaces, and protection rewrites crossing admission boundaries.

## Contract and failures

The engine describes source structure. Editor registry/mapping policy describes presentation and mutability. One resolved plan should serve paint, caret, selection, copy, and mutation. Viewport geometry is an input; parallel semantic booleans are not another policy authority.

A protection replacement must still satisfy the originating surface's write capability and clip. A donor's trusted bulk-operation shortcut cannot authorize arbitrary Sefer edits.

## Useful proof

Run a small selection of load-bearing donor invariants at the adopted public seam: protected deletion, range paste, one-gesture Undo, and exact-source structure reuse. Preserve the donor suite in its owner repository unless Sefer becomes the code owner. Do not copy its entire test count or snapshot output to demonstrate migration progress.

## Open questions

Who will maintain the editor core and publish changes? Which current direct core imports are acceptable during adoption? Do tables, sidebars, empty word boxes, and hidden wrappers have agreed visual behavior? Keep unsupported visual cases reachable in source mode without inventing a universal projection-confidence subsystem.
