## The rule: processes are machines, status is a classifier

- **Processes** (steps, waiting, failure, recovery) become machines: the git remote lifecycle
  (clone, fetch, push, combine, retry, refusals, stranded), the Writer consolidation, getting
  things onto disk and loading, tours.
- **Status derived from facts** stays a pure function. `syncStateOf` in
  `src/core/sync/state.ts` reads git and remote facts; a machine would hold a second copy of
  "we're ahead" that can disagree with the repository. Its chart comes from its rules made
  data (an ordered rule list plus a `satisfies Record<SyncState, SyncActionId>` action table).
- **`packages/editor` stays a pipeline.** No machine library in it; `pnpm boundaries` should
  enforce that, not a convention.

## The library

`@typeonce/effect-machine`: Effect 4, Schema-first, compound and parallel states, history,
`always`, final states, and every target of a conditional choice declared up front. Its
topology is captured from the declarations, and its devtools expose a serialisable
`MachineDocument`. Chosen over XState v6's `@xstate/effect` (experimental, on XState's `next`
branch, React-only bindings) and `@humanlayer/effect-machine` (targets live inside handler
functions, so nothing can draw it).

<Tradeoff id="fork" chose="Fork typeonce into our org" cost="We carry upgrades ourselves">
Pre-1.0 with breaking changes in minor releases, and its peer dependency is stable
`effect ^4.0.0` while Sefer is on `4.0.0-rc.112`. The fork loosens the peer dependency so the
first step adds one dependency and does not bump Effect. Moving to Effect 4 stable is its own
change, later.
</Tradeoff>

## How a chart is generated

<Mermaid id="pipeline" caption="From machine to the chart in the docs">
```mermaid
flowchart LR
  M["machine in src/core<br/>(.handle({...}) — plain data)"] --> D["MachineDocument<br/>(typeonce devtools)"]
  D --> T["toStateDiagram<br/>(ours, ~50–100 lines)"]
  T --> B["marked block in<br/>documentation/architecture/*.md"]
  B --> C["pnpm docs:charts --check<br/>pre-commit + CI"]
```
</Mermaid>

- `tools/docs/charts.ts` imports a short, explicit list of machines (not typeonce's scanner),
  so each chart lands in the doc we choose.
- Nested states become `state X { … }`, parallel regions `--`, guards edge labels, a choice
  with several targets a `<<choice>>` node.
- Output goes between marker comments such as `<!-- generated:remote-lifecycle -->`, the same
  trick as `pnpm lint:results`. `--check` exits non-zero if the file would change.
- Runs in Node like the unit tests; fine because `src/core` is free of browser APIs.

## Cancelling a clone: a delay, not a cancel

> cancellation doesn't really help a ton on git clone, because, like, at best, you have to
> just ignore the response. So I'd probably actually prefer his just add the delay, like the
> Gmail trick, add the delay with the cancel button.

Once the request for a zip is sent the bytes come back regardless; Effect's interruption only
lets us ignore them. So the lifecycle gets a short **pending** state before the network
request, with Cancel offered there (the Gmail "undo send" shape). Raised by the designer's
Claude on PR #7.

<Mermaid id="clone-delay" caption="The cancel window lives before the request">
```mermaid
stateDiagram-v2

  pending --> [*] : Cancel
  pending --> fetching : delay elapsed
  fetching --> writing : bytes arrived
  fetching --> failed : network / auth
  writing --> done
  writing --> failed
  failed --> pending : Retry
```
</Mermaid>

## Inventory: the implicit machines (2026-11-09)

> Find all of the implicit state machines in my app (there are probably a ton). Make the best
> decision that will elevate all three: the user experience (UX), developer experience (DX),
> and agent experience (AX) always, without breaking anything. Also, make state machines
> explicit.

Written against `f6885546`. Four readers went through every non-test file in `src/core`,
`src/app`, `src/platform`, `src/routes`, `src/dev` and `packages/`. **Everything below comes
from reading the code, not from running it**: "bug" means the lines as written allow it, and

There are about sixty. They fall into four shapes, and each shape wants a different tool.

shape.**

### What this changes in the plan

The plan above starts with the git remote lifecycle on a forked library. The inventory says
most of the harm is elsewhere and most of it needs no library:

1. **The two helpers first** (the action runner, and `createHeld` everywhere). Smallest
   change, most screens fixed, nothing in `src/core` moves. For people: no stuck spinners, no
   double sends, every failure says so. For us and for agents: one way to write a button
   that does something, and the building-blocks skill names it.
2. **Then the processes, one per commit, behind the functions that exist now**, starting with
   opening a project and record a version, written the way `repository.ts` `step` is: a
   tagged union, one `step(state, event)`, the transitions as data so the chart can be
   drawn from them.
3. **The status holes** as plain fixes alongside (they are a few lines each).
4. **The editor's four guards** as plain fixes in `packages/editor`.

### Measured against two rules, and what was ruled (2026-11-09)

The two rules: no helper extracted ahead of reuse, and no complexity for an unlikely race
without saying the failure, the likelihood and the cost first. Against them:

- **Stands:** the one-shot action helper (about 20 real copies), `createHeld` for loaders, and
  the failures that are not races fixed where they are.
- **Withdrawn:** the confirm-then-act row helper (the 8 copies differ on purpose), the one
  table over the five `SyncState` switches (five different mappings), and machines for the
  update check, the diagnostics writer, the migrate run, analysis status and sign-in (each is
  small and used once; a tagged union in the same file is enough).
- **Deferred:** the library fork and the chart generator until two machines exist; the
  "arriving" marker; the editor guards other than the typed marker.
- **Dropped from the ranking:** the backup journal and the save coordinator. Their case rests
  on windows of milliseconds.

Said of the races a person could plausibly hit. Done on branch `fix/plausible-races`, from
reading, none reproduced in the app first; `pnpm check` and `pnpm test:browser` pass:

- **Catalogue rows:** the busy id is a set, so one download ending no longer unlocks another's row.
