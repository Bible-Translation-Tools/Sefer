> The editor should be embeddable and testable in isolation. … we're not shipping a
> component. Wrapping it in a component of any framework should be trivial.

The editor becomes a workspace package written in TypeScript only. A host hands
it a parent element and gets back an object of methods and events. React, Solid,
Svelte or no framework: each is a thin wrapper. It comes before the [editor sharp
edges](/items/2026-10-14-editor-sharp-edges) (2026-10-15): copy, paste and Enter
tests are best written against the package's API, and the playground becomes
just another host.

> is probably an architectural boundary we should have started from beginning

The hub (wacs-dashboard-2) is the second host. Today it runs a read-only fork
(`spikes/viewer`, forked at Sefer 50aa9cd). Its `EDITOR-PIECES.md` lists what it
uses, what it added and what it wants.

## Decided (2026-10-15)

**The engine is injected, and it is always onion.**

> we can keep injected and yes bring your build. An ideal world might let you
> swap in a parser too, but we depend WAY too much on this cst/parser … So, I
> think that stays as assumed you're brining a build of onion.

The host passes `Analyze` and serves the wasm. Sefer brings galley and the hub
brings onion only.

**There is no built-in marker policy. The caller configures markers.**

> no on the s5 policy. a Caller hsould be able to configure their own custom
> markers and relax custom markers config

The package passes the engine's `setExtensions(list, { relaxZPrefix })` through
as configuration. Sefer's `\s5` policy (`src/app/legacyMarkers.ts`) stays Sefer's.

**It is a workspace package here, consumed by git tag**, the same way Sefer
consumes scripture-kitchen.

**No UI and no framework.** The hub's navigator, findings rail and source-compare
card stay in each host. The package exposes what a host needs to draw them:

- **Diagnostics.** What is drawn, as a lazy method plus an event that fires only
  when the set changes. This is the hub's `diagnostics()` / `onDiagnostics`.
- **Where.** Where the caret and the selection are, and where the viewport is
  (see the location API below).
- **Reveal.** Go to a range or an address: select it, scroll it a third of the
  way down, flash it. This is the hub's `reveal`.
- **Sync between instances.** Each instance only reports where it is and can
  be told where to go. The caller turns syncing on and off by wiring one
  instance's events to another's `reveal`:

  > it's another instance, and a caller can just turn on off their own sync
  > when sel / cursor changes happen

  The package can export a small `link(a, b)` that returns an unlink function,
  built on the existing `createAlignedGroup` (`src/editor/recipes/align.ts`).

## The location API (proposed)

> for any given selection or curosr, what toc range am i in, or one toc
> addressing unit would be sensible no?

Yes. The package owns `core/location`: the address type, the citation parser
(`mark 3`, `ROM 9:30-10:4`) and offset-to-address. It is about 735 lines of plain
TypeScript that the hub already wants. Everything a host sees is one unit, an
`Address`:

- **`where()` / `onWhere(cb)`** give the caret, or a selection, as an address. A
  selection is a range such as `ROM 9:30-10:4`. A caret in a heading or in front
  matter is the nearest unit the TOC has for it.
- **`viewport()` / `onViewport(cb)`** say what is on screen. This is today's
  `watchLocation`, a different answer from the caret's. Two views of one book can
  disagree here.
- **`reveal(address | range, opts)`** goes there. It is the same unit coming back,
  so sync is `a.onWhere(b.reveal)`. How it scrolls is the caller's choice:
  instant or smooth, where in the pane, and whether to scroll at all.

  > The main thing on linked scrollin gis you don't want it like crazy jerky or
  > force smooth or not smooth I think. I think a caller should deicde that as ui.

  The package reports and moves. It doesn't throttle, ease or chase. A caller that
  wants calmer linking debounces `onWhere` itself.

## Mutations and read-only

> how do we handle the mutation lifecycle. We run sous, but like, we do a callback on
> what it should on book mutation for example?

Yes, a callback. The editor-backed Book already has this lifecycle, and it is the
one Sefer runs Sous from today (`src/editor/book.ts`, the `Book` port in
`src/core/book/book.ts`):

- **`changes(fn)`** fires after an edit is accepted, with the `Change[]`.
  The host runs whatever follows: Sous, the findings, a save, sync.
- **`apply(changes, origin)`** is how a host edits: a fix, a Replace, an
  incoming sync. It returns a `Receipt`, or a `Refusal` when the editing rules
  reject it. It is the same write path keystrokes take, so undo sees it.
- **`source()`** is the text as it stands.
- **Diagnostics from the host come back in.** Sous's rows, or the hub's stored
  rows, are pushed in and drawn with the engine's as one set. Today that is
  `showCorpusFindings`; the package needs a setter for it.

The host owns everything after a change: the package does no analysis beyond
the engine call it was given.

**Read-only is a first-class switch**, settable at mount and changeable later
(`setReadOnly(bool)`). A read-only editor still reports `where` and `viewport`,
still takes `reveal`, and still draws diagnostics. The hub's `mountViewer` is the
editor mounted read-only, not a separate thing.

## What the package owns from core (proposed)

The package owns location, plus the narrow book and source types it uses (`Change`,
`SourceStamp`, `Origin`, `Receipt`, `Refusal`, `BookId`).

Engine types (`Analysis`, `NotePart`, `TOKEN`, `MARKERS`) belong with the engine's
bindings. Ideally scripture-kitchen ships them with the onion build, so a host's
engine and the package agree on them. Until then, the package keeps a copy.

**`core/fixes` goes in the package** (agreed 2026-10-15). It is 327 lines and depends only on
the Book and the engine's analysis. It does one job every editing host needs:
it applies the engine's own repairs and refuses one that has gone stale (the
analysis must describe the text exactly, and the revision must not have moved).
Without it, each host would write its own stale-range check, and that bug
produces plausible-looking scripture. It uses Effect's `Data` and `Result`,
which go with the rest of Effect.

### What ships as default behaviour (proposed 2026-10-15)

> I'm torn on whether to prebake recipe (footnotes as satellites) or let end users
> rediscover and configure. I..e. in our multibufffers in find, we pip verse
> number because that destroys alignment if you edit there … How much do we ship
> a default vvs just info?

**Ship Sefer's rules as the defaults, as named presets, each one switchable.**
Most of them protect the USFM rather than express taste, so a host rediscovering
them means a host corrupting text first. Examples:

- footnotes edited as satellites
- verse numbers protected in excerpt cards, because editing one breaks
  alignment
- the caret going around a passthrough marker

The package's job is to make the safe thing the default. The structure already
exists: `EditorPolicy` has a mode and presets, and `cardPolicy` is a preset.
The package exports these:

- `book`: the whole-book editor.
- `excerpt`: a card. Verse numbers are protected.
- `reader`: read-only.

A host picks one and overrides single rules.

**Attributes (`\w …|lemma=…`) are information only by default.** They are hidden
in Regular, and shown and editable as plain text in USFM mode, which is what
happens today. No attribute UI ships until a host needs one. It can come later
as a recipe, the same way footnote satellites did.

### Composing policies (proposed 2026-10-15)

> `editorPolicy({paint: hideVerseNumbers(),  versePerLine()})`… how do you merge
> policies like that and not allow creating something incoherent

This is already built, as data, in `src/editor/core/registry.ts`:

- **A table.** Every class of text (`slot.v`, `note.caller`, `chrome`, …) has a
  cell. A cell is a paint (`point` / `boundary` / `ambient` / `none`) and a
  mutability (`direct` / `via-anchor` / `trusted-only` / `immortal`).
- **Presets are patches.** A preset is a partial patch over that table
  (`PROJECTIONS`: `lock-verse-numbers`, `hide-notes`, `note-satellite`,
  `lock-structure`, …), and the patches fold in order.
- **Last wins**, per class and per field.
- **Coherence is checked when the policy resolves, not by type.**
  - `resolve()` clamps what can be made coherent. A hidden thing that is still
    mutable becomes a pip, or a frozen set. Each clamp is listed in
    `Assignment.clamped`.
  - It throws on the rest. The struck cells are a named table (`STRUCK`), so an
    unlawful combination is a caught error with a reason, not a strange screen.

`{ mutableVerseNumbers, hideVerseNumbers }` is the clamp case: the verse number
becomes a pip that you edit through its anchor.

For the package:

- **Presets become typed values, not strings:**
  `editorPolicy("regular", lockVerseNumbers, hideNotes)`. Each one is an
  exported `AssignmentDelta` constant, and a host may write its own patch.
- **No type wizardry.** A single cell is a 4×4 matrix, so its struck pairs
  could be a type. But coherence across classes depends on how cells relate,
  such as the owned sets that hide together, and a type can't express that
  without becoming unreadable. Instead:
  - `resolve()` stays the judge.
  - The package exposes it, so a host can check a policy at startup.
  - One test resolves every combination of the shipped presets: there are
    about eight, so 256 combinations.
- **Three named groups**, as above: `book`, `excerpt` and `reader`.
- **Agreed (2026-10-15):** typed preset values, and a host may write its own patch.
- **A policy can change live.** `setPolicy(policy)` replaces `setMode`, since a
  mode is just the first patch. Today this is a CodeMirror `Compartment`
  reconfigure in five files. Inside the package, one call does all of it:
  - re-resolves
  - repaints
  - keeps the scroll anchor (BookEditor's flip anchor)
  - re-lints (the `needsRefresh` bug)
  - hands the new patches to the Book, so a satellite's edits are judged under
    the policy it now shows

<Followup id="extensions-global">

The engine's `setExtensions` applies to the whole page, not to one editor, in
the onion-only build too. Onion keeps the registry in a process-wide static:
`scripture-kitchen/onion/src/extensions.rs:216`, `static REGISTRY: RwLock<…>`,
bumped by a global `GENERATION`. Galley only wraps it.

So two editors on one page with different marker configs interfere. The lexer
already takes the registry as a parameter internally (`marker_idx(…, ext)`,
`lex_with`). An ask for scripture-kitchen: a parse door that takes extensions
per call, or a handle per registry, with the global kept for callers that want
one. Until then, the package documents one marker config per page.

</Followup>
