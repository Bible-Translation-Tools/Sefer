State that belongs to a project and outlives a session: proofreading suppressions ("this finding
is fine here") and key-term approvals. Reference picks are already built this way (per device,
`.sefer/project.json`). Today approvals live in memory for the session and nothing persists
suppressions.

## Two mechanisms, one helper

<Question id="one-or-two" answer="Two (2026-10-20): the lifecycles differ. One small helper for a versioned JSON file in `.sefer/` serves both.">One mechanism for approvals and suppressions, or two?</Question>

Will, 2026-10-20: approvals have states (approved, approved with edits) and must show when the
verse changed since; a suppression is just "ignore it", but its list wants pruning when what it
named goes away. So:

| | Approvals | Suppressions |
|---|---|---|
| File | `.sefer/key-term-approvals.json` | `.sefer/sous-chef-suppressions.json`, and `.sefer/onion-suppressions.json` for lint |
| Key | book/chapter/verse + term | the engine's identity (below) |
| Stored | hash at open, hash at approval | the identity, when (a note: deferred) |
| Changed text | stays, badged "changed since approved" | goes stale; pruned |
| Shown | a badge and a count on `/terms` | the finding hidden; a count of hidden |

**Named by subsystem** (Will, 2026-10-20). One file per engine also means each file follows its
own identity format: when Sous moves to `v2`, only `sous-chef-suppressions.json` migrates.

**A note on a suppression** (the reader's reason) is deferred: not in the first version.

**Where it applies: one partition, read by everything.** Suppressions are a `reduce` over the
findings into `{ shown, suppressed }`, in core beside `hideStale`
(`src/core/findings/filter.ts`). The editor's diagnostics, the Findings panel and its totals all
read `shown`; the count reads `suppressed`. Nothing draws a finding and then hides it.

Approvals hash with Galley's `hash(text)` (XXH3-64, seed 0, as `sourceHash`) and name the
algorithm in the header, so a change marks entries "needs re-check" rather than dropping them.

## Key-term approvals

- **Unit:** the verse a hit is in (its TOC unit), not the card's clip. Keyed by address and
  term, because one verse can hold several terms.
- **Stored:** the verse's hash when the card opened, and the hash at approval. Nothing else.
- **Every state but "unapproved" is derived** from those two hashes and the verse's current
  hash, so nothing has to notice an edit: the state is read when it is shown.

## Proofreading suppressions: the keys

Kitchen **did** ship stable identities (d526de8, in v0.1.10:
`@wycliffeassociates/scripture-kitchen/sous-identity`; contract in `galley/sous-messages.md`,
"Stable identity"). This item said otherwise until 2026-10-20; Sefer does not use them yet.
None is built from offsets:

| Identity | Means | Built from |
|---|---|---|
| `v1:s:…` | this text here is fine | verse, the flagged text, how many identical texts come before it in the verse |
| `v1:f:…` | this rule is wrong here | the rule, then the same three |
| `v1:p:…` | this claim is fine anywhere | the rule and what it claims (the glyph, its neighbour…) |

### The ladder: here, everywhere, never

Will, 2026-10-20: `v1:p` was built for the middle rung.

> "particle particle" is always right, but don't disable doubled words

So a reader has three answers, from narrowest to widest, each worded by what it allows:

| Says | Allows | Stored as | The rule still watches |
|---|---|---|---|
| **Fine here** | this occurrence | `v1:s` (site) | everything else, including the same thing elsewhere |
| **Always allow “…”** | this exact thing, anywhere in the project | `v1:p` (pattern) | every other word, mark or pair |
| **Turn off this check** | the whole check | Sous settings, per project | nothing |

The middle rung always names what it allows, quoted, so it never reads as a switch: "Always
allow “particle particle”", not "Allow doubled words".

**Each option says what it will do**, in a line under its label, with the check's own words
filled in:

| Option | Its line |
|---|---|
| Fine here | Hide this one. It comes back if this text changes. |
| Always allow “particle particle” | Never flag “particle particle” in this project. Other doubled words are still checked. |
| Turn off this check | Stop checking doubled words in this project. Turn it back on in Settings. |

Will, 2026-10-20, agreeing:

> v1:s is the more natural way people think of, ok, this text is correct. … for as it stands, I
> approve this verse so to speak.

**`v1:f`, and why it is not offered.** `v1:s` says "this text is fine": it hides whatever flags
the spot. `v1:f` says "this rule is fine here": another rule flagging the same spot still shows.
They differ in two cases:

- A settings change makes a different rule flag the same text (Placement before, RunShape
  after). `v1:s` keeps it hidden; `v1:f` shows it again.
- One spot has two real problems and the reader dismisses only one. `v1:f` keeps the other;
  `v1:s` hides both.

Sous reports one rule per spot (the headline), so the second case is rare, and "fine here" as
`v1:s` is what a reader means. `v1:f` costs kitchen nothing (it is `v1:p` plus the site) and is
there if a precise "this rule only" is ever wanted.

**What "always allow" means for each check** (the pattern's key, from `sous-identity.ts`):

| Check | “Always allow …” | Example |
|---|---|---|
| Doubled | this word doubled (bare, or separated by punctuation) | “particle particle” |
| Casing | this word in this casing | “lord” in lower case |
| WordLength | this word | an unusually long name |
| Placement | this mark on this side of this kind of character | “—” before a digit |
| ExactNeighbor | this mark followed by that one | “'.” |
| PooledNeighbor | this mark beside this kind of character | “«” beside a space |
| RunShape | runs of this mark of this size | “...” |
| LetterRun | this letter repeated this many times | “sss” |
| Rarity, SentenceStart | this character, anywhere | “ʼ” |
| BookRate | this mark's rate in this one book | “;” in Psalms |
| Hygiene, Presence, SourceCopy, LengthProportionality | no middle rung: fine here, or turn off | |

Rarity and SentenceStart key only on the character, so "always allow" there is close to
turning the check off for that character, which is what someone means.

**The same ladder for lint** (onion), with [kitchen ask 15](/items/2026-09-14-scripture-kitchen-asks):
"fine here" is a site identity for a diagnostic; "always allow" needs a subject, e.g. an
unknown marker by name ("always allow `\zqq`", without turning off unknown-marker findings).
Registering a marker as an extension, as `\s5` is, is the stronger form of the same thing.

**Why `v1` and the letters:** `v1` is the format's version, so a saved identity can be migrated;
the letter is the scope (`s` site, `f` finding, `p` pattern). Readers never see them; the plan
and the code call the rungs "here", "everywhere" and "off".

<Question id="ladder-where" answer="&quot;Fine here&quot; on the card; the other two behind More, and the tutorial says why (Will, 2026-10-20).">Does a finding card show all three options, or "Fine here" with the other two behind a "More"?</Question>

**Fixing something else in the verse does not bring a "fine here" back.** `v1:s` is not a hash
of the verse: it is the verse's reference, the flagged text itself, and its ordinal. Fix a typo
elsewhere in the verse and the quotes you allowed stay allowed. It comes back only when:

- the flagged text itself is edited (a new site, judged again);
- an identical text is added or removed EARLIER in the same verse, which shifts the ordinal.
  For a common single mark (`—`, `"`) that can happen; it is rare, and costs seeing one finding
  again;
- the verse is renumbered.

### Where each is stored, and when it is read

- **`.sefer/sous-chef-suppressions.json`** holds both rungs: `here` (`v1:s`, with when) and `everywhere` (`v1:p`, the same). Turning a check off stays in Sous settings.
- **Read when the first analysis publishes**, not at app load: suppressions filter findings, so
  they are needed when findings are, and not before. One small file per project.
- **`.sefer/key-term-approvals.json` is read when `/terms` opens** (Will, 2026-10-20), never at
  app load; nothing else reads it.

### Staleness and pruning

A site identity names text, so whether it still applies can be read off the text, with no
analysis and no settings in the way:

- **Stale:** the verse no longer holds the flagged text at that ordinal. The suppression goes
  (pruned when the book's suppressions are next read or written).
- **"Always allow" is never pruned automatically**; it is listed where suppressions are managed.
- **Not stale because the finding vanished:** a check switched off hides the finding but leaves
  the text. Pruning on "matched nothing" would lose those, and switching the check back on would
  bring them back unsuppressed. So prune on text, not on matches.

### Still open in this scope

<Question id="verse-text" answer="Raw USFM, always; never a normalised or reading-text version (Will, 2026-10-20). Reasons and the edge cases below.">The ordinal counts identical texts earlier "in the verse". Which text is the verse: the raw USFM of its TOC unit, or the reading text?</Question>

**The verse is its TOC unit's raw USFM**, markers included: the same text the finding's offsets
slice, which Sefer already holds.

The one alternative is the reading text (galley's mask: what Sous actually judges, without
markup). It would be steadier in one case: a markup-only edit earlier in the verse can shift an
ordinal, because raw counting sees marker characters. Suppress a `*` or a `+`, then add a
footnote before it (`\f + … \f*`), and the count of earlier `*` changes, so the finding shows
again. It is still raw USFM, because:

- **Raw text cannot be redefined.** The mask can: if what it hides changes (notes in or out,
  a new marker kind), every saved ordinal moves at once, which is a format change and a
  migration. Raw USFM only moves when someone edits it.
- **The failure is visible and small.** A shifted ordinal shows one finding again; it never
  hides one that should show.
- It needs no projection to compute, and is the same text on every mode and surface.

**What the reference is:** the unit's Address from `unitAddress`
(`packages/text/src/location/locate.ts`), in the canonical book code, never a localized name:
`GEN 1:2`; a segment `GEN 1:3a`; a bridge `GEN 1:1-2`; a list by its hull (`\v 1,3,5` is
`GEN 1:1-5`); text before verse 1 (a heading, a psalm title) by its chapter, `PSA 3`; the
introduction `GEN intro`. Whatever string Sefer formats it to is saved, so the format is fixed
once shipped.

**What should bring a suppression back, and does:**

- Renumbering the verse, splitting a bridge or a segment: the reference changes, so the
  finding shows again and the old entry is pruned. That is right: it is a different verse now.
- Editing the flagged text itself.

**Accepted edges:**

- A markup-only edit earlier in the verse that adds the same characters (above). Rare.
- Two verses with the same number in one chapter (itself a finding): they share a reference,
  so "fine here" on one also covers the same text at the same ordinal in the other. Rare, and
  fixed by fixing the numbering.

<Question id="approval-key" answer="Term + verse, no guide (Will, 2026-10-20): the guide's prose changing should not touch an approval.">An approval's key: the guide, the term and the verse?</Question>

**An approval is keyed by term id + verse reference.** A guide is one file per gateway
language (`fixtures/stet/en.json`, `es-419.json`, `pt-br.json`); a term's id is its ENGLISH
label, slugged, with a counter on collision (`idsFor`, `src/core/stet/stet.ts`), so the same
term has the same id in every guide, and a project that switches guide keeps its approvals. The
guide's prose (definitions, glosses, its frozen readings) is not in the key, so changing it
touches nothing.

whose labels collide (`love`, `love-2`). Upstream has no stable identifier. An approval whose
term is no longer served goes dormant (kept, shown nowhere) until the term returns; no UI is built
for it. Approvals also fill
`Term.done`, which is 0 today for want of a store.
