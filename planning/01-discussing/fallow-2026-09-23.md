# Fallow: a first pass, and whether it should own boundaries

**Status:** 2026-09-23. One working session with fallow 3.28.0 (`npx fallow`, MIT). Cleanup commits are on master; this file is the part that needs a ruling.

## Why the 457 unused exports stay

Nearly half are barrel re-exports (`src/editor/index.ts` alone has 105): the editor's and core's deliberate public surface, which the next screen will pull from. Most of the rest are ported-spike instruments (`timing`, `trace`, `inspect`), Tauri `*Live` layers the desktop composition doesn't reference by name yet, and registry predicates. Removing `export` from 283 symbols is a lot of churn for you to review, and it deletes things the build-out is about to want. That's the opposite of low-hanging fruit.

If you ever want this gated, fallow supports a baseline (`--save-baseline` / `--baseline`), which fails only on *new* dead exports. That's the only form I'd put in `pnpm check`.

`bootEndpoints` is documented in `configuration.md` as what the Network card reads, but nothing calls it. Either the card or the doc has drifted. I left both alone.

## Health, for the record

The score is dragged down by component size, not by tangled code (average cyclomatic complexity is 2.3). The biggest functions: `ReviewPanel` 1035 lines, `makeShell` 844, `mountAnnotator` 761, `registerShellCommands` 718, `Find` 713, `FindingsPanel` 603. The highest-complexity functions sit in the editor's structure builders (`buildRegular`, `scanCst`, `buildStructure`) and the diff (`inlineDiff`, `diffRuns`). All of these are "when you're next in there" items, not cleanup-session items.

## Boundaries: my opinion

**Keep `tools/boundaries/check.ts` as the authority. Don't move it to fallow.** You might later add fallow's zones *only* for the layer-direction rule nobody enforces today. Even then, I'd lean towards adding that rule to our checker instead of running two boundary tools.

I tested this instead of reading the docs: I wrote our rules as fallow zones plus a rule pack, and ran it against today's tree (clean per our checker) and against a probe file with one of each violation our checker catches.

| our checker catches | fallow |
| --- | --- |
| `node:*` in core policy (any builtin) | **missed.** Specifiers are package names, not prefixes, so every builtin would have to be listed |
| `solid-js`, `@solidjs/*`, `@codemirror/*`, `@effect/platform-node/*` | caught (`banned-import` rule pack) |
| `import("isomorphic-git")`, a dynamic import | **missed** |
| `import.meta.glob("../app/*.ts")` escaping core | **missed** |
| `../app/env` relative escape | caught (zone rule) |
| core tests may use Node | needs a separate tests zone listed first; doable |
| a file not yet reachable from any entry | **not checked at all.** Fallow analyses the reachable graph, so a new core file escapes until something imports it |
| "nothing outside src/dev *statically* imports it" | **can't express.** Fallow doesn't tell static from dynamic imports, so it flags the four legitimate `__SEFER_DESIGN__` / `import.meta.env.DEV` lazy routes. That means four suppression comments on exactly the lines that *are* the production gate |
| `window.location`, `document.title` (reads) | missed (it matches calls, not property reads). Oxlint covers these anyway |

What fallow would add:

- **Layer direction.** `editor` ↛ `app`, `platform` ↛ `app`, `core` ↛ everything. Today only "core is sealed" and "dev is sealed" are enforced. The trial found no violations, so this would be a free ratchet.
- **"Engine only through core/galley".** Our doc said it; nothing enforced it. The trial's only hit was `platform/web/galley.ts` taking the `.wasm` as an asset URL. That's legitimate, and the doc now says so.

So: fallow's boundaries are good at directory-to-directory rules and weak at exactly the cases our checker exists for. Ours resolves seven specifier forms and walks the directory rather than the import graph, which is why it catches what fallow misses. Replacing it would lower the bar. Running both would give us two configs that describe one architecture, and they'd drift. That's the same two-records-of-one-fact problem the Galley manifest had.

If you want the direction rule, it's a layer table in `check.ts` (roughly a `from → allowed` map applied to the relative-import branch it already has), plus the one engine rule. I'd do that before adopting fallow boundaries.

## Where fallow does earn a place

The dead-code, cycle and duplication passes found real things in minutes, and three of their checks are at zero right now: unused files, unused dependencies, circular dependencies. Those are cheap to keep at zero:

```sh
npx fallow dead-code --unused-files --unused-deps --circular-deps
```

That could go in `pnpm check` / CI as a gate, pinned (`fallow@3.28.0` as a devDependency, not a floating `npx`). `dupes` and `health` stay advisory, run by hand before a cleanup session. `similar-code` needs a ~300 MB local model and says itself that it isn't for CI.

**For you to decide:** (1) gate those three checks or not; (2) the layer-direction rule in our checker, or not yet; (3) whether `bootEndpoints` / the Network card doc is drift to fix.
