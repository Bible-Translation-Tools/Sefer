Resource kinds: shared domain ideas, not four apps in one

plan review · Sefer master 4a05258 · planning/01-discussing/resource-kinds-2026-10-01.md (the distilled plan) + the 2026-10-01 conversation · WACS and Language API checked live

01 Plan summary

Sefer is about to hold things that are not scripture text: Macula's syntax trees, Translation Notes, Questions and Words. The plan is to add them as kinds that fill a small, shared capability record, so a new resource is an adapter plus a renderer, never a fifth application.

Today the only presupposition of USFM is one chain: /project/$slug opens a Project, a Project is a folder of .usfm Books, the engine parses them, and its TOC gives every Address. Source and Book are already text, not USFM; the Library already keeps kind, subject and per-project role apart and binds tn/tw/tq that nothing reads. The plan leaves the Project chain alone and puts resources beside it, bound by role.

Scope: ~6 new core modules and 4–6 adapters, 3 existing files generalised (library.ts, import.ts, shellEvent.ts), one new UI registry, one new primitive. No file is deleted; no existing USFM behaviour changes. Edit for TN/TW is typed, not built.

The core insight. One closed union of content kinds, consulted in exactly two places — recognize() at the import boundary and a renderer registry at the screen. Between them sits a capability record (info, places?, search?, edit?) that nobody discriminates on: panes check for a slot, never for a kind. Every per-kind component speaks to the rest of the app only in Address. Every call returns an Effect, consumed by a Solid 2 async memo that holds the last answer.
Kinds in hand: Macula Greek/Hebrew (wasm blob, below-verse, faceted search, read-only) · TN (29,300 Markdown chunk files, 14 MB, verse-addressed) · TQ (sparse first-verse files, open ranges) · TW (1,011 slug-keyed articles, not verse-addressed without a TWL).

The two-place rule
Boundary. recognize(metadata) reads the RC identifier/type (tn+help, tq+help, tw+dict), a Burrito flavor, or a Macula blob header, and returns one member of the closed union — or refuses. Kitchen terms: this is the only place that looks at the ingredients' labels.
Between. Core, panes and workflows see a ResourceHandle. They ask if (handle.places), never if (kind === "tn"). Adding a capability is a new optional slot; every existing adapter compiles unchanged. Adding a kind is an adapter that fills a subset.
Screen. The renderer registry is the second and last switch (kind). Rendering is the one job where knowing what a thing is is the point: Macula's faceted builder, RTL text and hover are its own DOM. It receives the handle; it never reaches into storage or another kind.
05 Three tiers & today's leaks added 2026-10-01 pm

The shared domain is not one layer but three. The fear of "four apps in one" is really the fear of a tier-3 idea living in a tier-1 module. Name the tiers, let a module depend downward only, and every "what about diffing / clipping / editing / commenting" question answers itself by asking which tier it is in.

Two consequences the plan doc now carries

A kind plus a reader: normalizationtier 2 · resolved
Where it lives is the container's job and already decoded: a burrito's ingredients carry path, scope, mimeType per file; an RC's projects[] carry identifier + path, and dublin_core.format names the MIME type once. What it is varies by format, not container: WA en_tn is Markdown per chunk, unfoldingWord tn is TSV per book — both kind tn.
So: recognize() returns a kind and a reader, one reader per (kind, MIME type), every reader yielding one internal record — for a note: Address, ordinal, Markdown body, optional quote. A reader is pure (bytes + scope → records) importing only address.ts, which is why it belongs in src/core and would extract cleanly to a utilities repo later.
The fragment: one generalization with payofftier 2 · one carve-out
"TQ beside the project in a multibuffer" is the excerpt card: a fragment of a document at an Address range, shown as a satellite. Generalize from "a range of a USFM Book" to "a range of anything with places()" and clip, align and follow all fall out of one type.
Cost to decide first: the excerpt card obeys surfaces are judged, not trusted — a tier 3 rule, because it has an engine projection. A TQ fragment has none. The generalized fragment needs an explicit "no projection, read-only" case, decided before the first non-USFM satellite.
TQ needs a table of contents it does not havetier 2 · versification
gen/01/01.md means "from verse 1 until the next file"; the last file in a chapter needs a verse count, and "you referenced a verse that does not exist" needs the same thing. TQ, TN and TW are ULB-numbered. The only TOC Sefer has is the project's — tier 3, from the engine.
If TQ is built: places.at(address, ctx) takes a TOC handed in, refuses unresolved without one. Tier 2 eventually wants its own versification table (STEP's TVTMS) so a resource's TOC does not depend on which project it is opened beside. Named, not solved — open question 1.

Default find, the haystack, and the 27k-file wrinkle

Find already has the three stagestier 1 · exists
core/search/reading.ts: a Subject (id, text, stamp?) is one haystack unit; a Reading is that subject prepared — toSource(at) maps back, pieces() says when a span crossed dropped markup; a Hit carries its stamp. Pipeline: scope → prepare → match → map back.
Default: the identity Reading (toSource = at, one piece). USFM overrides one stage — its Reading is cut by Galley's mask; Galley owns that lifecycle and keeps owning it. The override point a kind supplies is the haystack, documents(): USFM's are Books, a folder's are files, TN's are whatever its adapter hands back.
29,300 files is a haystack problem, not a find problemtier 1 · derived store · measured
Three things USFM already keeps apart stay apart for TN: on-disk layout is upstream's (git, export, edit unit — never reshaped); the derived store is per-book packed JSON, an index rebuilt from disk and stamped, exactly as the engine's TOC is for USFM; the edit unit stays the chunk file, and an edit or a pull invalidates that book's pack.
So: documents() reads the pack, one book in memory, async load on book switch. Editability costs nothing. Web: read-only TN is packed only, fetched as one archive, no raw tree — 27k OPFS files and Web git over them are the real cost. The raw tree is required only for editing TN on the Web: decide then (open question 6).

The shape was wrong upstream; don't adapt around itdecision
An adapter from a packed on-disk layout back to the upstream git layout is the wrong direction. A Gitea release could carry the per-book JSON beside the repo, and the Web then reads one object per book with no tree at all — but that kills writability, which is the real cost of 29k files having been the format instead of SQLite or per-book files.
Rule: read-only on the Web = packed, from a release or a direct-pack import, never a raw tree. Writable TN = desktop (real files, git2) until there is a reason otherwise. Consolidation upstream (TSV or one file per book) is the content-team ask that would make Web writability cheap; the reader-per-format design makes that a new MIME reader, nothing more.

worked query · πίστις Χριστοῦ Everywhere Greek has πίστις with genitive Χριστός in the same noun phrase, how did this project render it, and consistently? ① lookup both lemmas. ② run({ target: "constituent", filters: { class: np }, contains: { lemma: pistis } }) → every NP containing πίστις, with term. ③ The package allows one contains, deliberately — so the adapter applies the second condition: word(term).ancestors finds the NP, its words are checked for Χριστός in genitive; all sync and local, milliseconds. (Intersecting two passages() at the verse answers "both somewhere in the verse" — not the question.) ④ Survivors collapse to Addresses. ⑤ The project resolves each through its TOC into an excerpt; the multibuffer shows every rendering side by side as satellite editor views; the reviser fixes the odd one out in place. Two package asks fall out of ③: a second contains or an and, and a constituent id on Hit.
what it stresses Platform-only adapter · lazy open with progress · a source of truth that is not text · a kind overriding search · answers below the verse · a different versification (WLC: open question 1 bites here first) · its own RTL DOM · read-only with no files at all. Every other kind is a subset of that list.
A kind with no tier 1: bespoke, and it stays bespokeContainerKind "builtin"
documents?, edit? and file naming are as optional as search?; a handle is info plus what the kind has. Resource.root is required today and Macula has no root — but Macula is built in: URL and checksum compiled into the adapter, no manifest, recognize() never involved.
Light answer: a third container kind, builtin, whose root is the path of the one cached object. root stays a string, library.json keeps its shape. Generalising root to "directory or blob descriptor" waits for a second blob-shaped kind. The point: a bespoke kind integrates cleanly without bending the common path.
Enhanced find = a kind's search panel through the same registrytwo-place rule, again
Find today is one screen: text find over project + references. When a bound handle has search, Find gains that kind's panel beside the text find; the registry supplies the panel as it supplies the pane.
One result shape for every panel: Addresses, optionally with the kind's own hit cards (Macula's run() spans). Addresses → multibuffer; cards stay in the panel. Find never learns what a facet is; text find never learns about lemmas.
Hover splits in two; only one half is Macula'sopen question 2
Hover in Macula's own pane (word(term): parsing, gloss, ancestors) is inside its DOM and free. Hover a word in the project's text and see its Greek is cross-text and needs an alignment — word-level data in the project's USFM (\zaln).
Rule: the kind does not create that capability; the project must carry the alignment first. Until then, Macula emits only the verse Address.
No Macula-shaped bump in the recordsecond-implementer rule
Facets, presets, the word card, RTL reading: Macula-only, so they live in Macula's pane and panel, not in ResourceHandle.
Rule: a slot enters the shared record when a second kind implements it. That is the difference between "Macula fits" and "the interface was shaped around Macula".

08 Risk assessment
Name collision on kindhigh · assumption
The plan's "kind" is the code's Resource.subject territory, and ResourceKind already names the container. Six importers, one persisted file.
Mitigate: rename in one commit before any adapter; ContainerKind/ContentKind, and keep subject as the raw string it is.
Versificationhigh · edge case
WLC Hebrew numbers Psalm titles, Malachi 4, Joel differently from English. Macula Hebrew against an English-numbered text is where it bites first; TN/TQ/TW are ULB-numbered and mostly escape.
Mitigate: the plan names it (open question 1) and does not hide it in an adapter. Keep it that way: info.versification on the handle, a mapping primitive later; STEP's TVTMS is the dataset.
en_tw is 629 MB on WACShigh · assumption
The plan's TW numbers (1,011 articles, 5.75 MB TN) describe the content, not the repo. A clone with history: "latest" still fetches tWs_for_PDFs and archive.
Mitigate: fetch bible/ only (Gitea contents API, or sparse checkout on desktop), or a packed release artifact — the TN import plan's "if we control the distributed resource" path.
pnpm deadcode vs "typed, not built"medium · ordering
release.yml's verify runs fallow before every deploy; an unused WritableUnit type fails it.
Mitigate: give edit one consumer (the registry's exhaustive render reads handle.edit !== undefined to choose read-only), or a documented .fallowrc.jsonc entry per lint-results.md.
TQ open ranges need the textmedium · edge case
gen/01/01.md means "from verse 1 until the next file"; the last file in a chapter needs a verse count. 17 files for Genesis 1's 31 verses.
Mitigate: places.at(address, ctx) takes the project TOC; the adapter refuses with unresolved when no TOC is supplied rather than guessing.
Macula below the versemedium · edge case
Hits carry word/morpheme positions; Hebrew morphemes share a word address. The interface stays at Address; aligned word highlighting in the project's text would need a finer answer and the project's own alignment.
Mitigate: open question 2 stays open; the Macula pane highlights in its own text, emits only the verse Address.
Cache outliving its datalow
Handle answers are cached by identity; a re-import of the same version must hit, a new version must miss.
Mitigate: info.identity is the Fingerprint rule from location.md applied to resources (Macula: the blob checksum).
Rollbacklow
Additive. Removing the kind table leaves library.json with an extra field the schema can ignore. No migration of folders (the uses addendum defers that explicitly).

Cognitive complexity — "you'll forget how this works in a month"

The two-place rule lives in memorymedium
Nothing stops a third switch (content) appearing in a workflow six months from now, and the whole design is that there are two.
Mitigate: a grep gate in the style of dev-only-routes.md: ContentKind may be narrowed only in recognize.ts and registry.tsx. Cheap, and it turns the rule into a check.
Hold-last-answer is a contract, not a stylemedium
If one pane hand-rolls its own pending state, panes will flicker differently and the "feels synchronous" property dies by a thousand cuts.
Mitigate: the Held primitive is the only way a pane consumes a handle; say so in ui.md's primitive inventory.
from on place eventslow
A pane that emits an Address and also follows Address will echo itself unless it ignores its own from. Action at a distance.
Mitigate: Held/the pane wrapper filters from === self once, centrally; a comment on the variant says why from exists.
Why Effect, when everything is locallow
The next reader will ask "why is this async?" and the plan doc's answer (remote resources) is not the real one.
Mitigate: the handle's doc comment states the actual reasons: one colour, interruption on caret-follow, typed unavailable. Update resource-kinds.md's "Every call may be async" section to match.
09 Plan review

Good

  • It leaves the Project chain alone. The dangerous version ("swap the editor at the router") was rejected in conversation; resources sit beside a project, bound by role, exactly as library.ts's header already describes.
  • Capability presence, not kind. Adding a capability is a new optional slot; adding a kind is a subset. Strongly typed in both directions, which is the stated goal ("if something changes shape it's easy to plug in").
  • Address is already the shared vocabulary. core/location is text-independent by design (location.md: "No offsets, no text, no hash"). Macula's Passage maps in one line; nothing new is invented.
  • Edit typed, not built. Matches the build-out rule and the memory note; makes the Book-is-text question answerable later by compilation.
  • The pending policy is stated as a rule, not left to each pane.
  • The plan doc already read the real data (chunk files, duplicate headings, TW's config.yaml index, Strong's join) and changed its mind in writing — the second pass retiring "plugin" is the right kind of revision.

Bad

  • Name collision with the existing ResourceKind (§5.1). The plan doc describes the Library correctly in the addendum and then reuses the word.
  • No arrival path on the Web. The Language API has no helps (§5.9); the plan assumes TN/TW exist locally.
  • Stale repo facts. en_tn_condensed and WA-Catalog/en_tw vs today's WycliffeAssociates/en_tn and a 629 MB en_tw.
  • ShellEvent ripple unaddressed: booksOf() and three subscribers.
  • pnpm deadcode will reject the "typed, not built" slot unless it has a consumer or an entry.
  • Docs: services.md's Library entry ("Scripture only…") and a new architecture chapter are not in scope but must change the day the first adapter lands.

Ugly

  • Four kinds, four very different shapes, and only Address is truly shared. TW is not verse-addressed at all without a TWL. The record risks being info plus four optional slots each filled by one kind — which is fine, but then the "shared domain" is thinner than the plan's prose suggests. Be honest that the floor is info + release.
  • Macula owns its DOM and its search vocabulary. That is correct and also means the "faceted find" is a one-implementer interface. The plan doc says so ("Dedicated"); keep it out of the shared record unless a second corpus appears.
  • Effect everywhere for local work is a tax every pane pays. Small, and the conversation accepted it knowingly — but Held must make it invisible or it will be resented.
  • TN through Book is the elegant answer and the one most likely to surface USFM assumptions in the admission rules and the save/recovery model. The plan leans; it does not commit. That is the right posture now, and a trap if the first edit ask arrives mid-sprint.

Questions for Will

  • Event or signal? A place.focus ShellEvent variant (one vocabulary, traceable) or a separate shell.place signal (ShellEvent stays about Books)?
  • Which proof first? The plan says Macula Greek read-only (hard case: below-verse, facets, wasm, platform Layer). TN read-only is the common case and exercises recognize, chunk ranges and Held with no new dependency. Which risk do you want retired first?
  • TW behind /terms? The plan's own observation — TW is nearly a STET Term — suggests the cheapest TW integration is not a pane at all. Is that in or out of this work?
  • Helps in the catalogue: an API ask (add subject/type to vw_consolidated_repos) or a second source in Sefer?
  • Does uses on a project (the 2026-10-01 addendum) happen alongside this, or wait? It changes what the source picker offers and where folders land.
