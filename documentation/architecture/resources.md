# Resource metadata

Scripture Burrito `metadata.json` and Resource Container `manifest.yaml` describe what a resource is. Sefer may receive those bytes from the `effect/FileSystem` port or from a Rust command behind Tauri; either way what reaches the application is an untyped JSON value. `burrito.ts` and `resourceContainer.ts` in `src/core/resources/` are the contract that turns such a value into a typed one, and they are nothing else: no reader, no I/O, no classification, no import flow. The rest of the folder — intake, classification, the Library — is below.

Two Effect Schemas, with the same decode shape — a synchronous `Schema.decodeUnknownResult` wrapper that takes `unknown` and returns `Result<T, Schema.SchemaError>`, never an Effect, so a caller on any path can decode without a runtime.

- `burrito.ts` — `decodeBurritoMetadata`. Requires `format` (the literal `"scripture burrito"`), `meta`, `identification`, `type`, `languages`, and `ingredients`; `idAuthorities`, `localizedNames` and `relationships` are optional.
- `resourceContainer.ts` — `decodeResourceContainerManifest`. Requires `dublin_core` and `projects`; `checking` is optional. It decodes a parsed value; `projectMetadata.ts` parses `manifest.yaml` (the `yaml` package) before handing it over.

Both model a subset — the fields the previous application actually read, plus enough to identify a resource. Both are open records: Effect Schema ignores excess properties by default, so a real Burrito or manifest carrying spec fields we do not model still decodes, and the unmodelled fields are simply not carried into the decoded value. Adding a field to a schema is how it becomes visible to the rest of the application.

A refusal is a `Schema.SchemaError` whose `message` names the failing path, for example `Missing key` followed by `at ["identification"]`. Fixtures live in `fixtures/resources/`; see that folder's README for what is real and what is constructed.

## The source texts a project declares

`relationships.ts` reads what a project says it was translated from, whichever format said it — Burrito `relationships[]` with `relationType: "source"`, a Resource Container's `dublin_core.source[]`, or a BTT Writer manifest's `source_translations[]` — into one `RelatedResource { language, resource, version? }`. `ProjectMetadata.related` carries every listed version as written; `highestVersions` keeps one per language and resource, the highest listed, because a project that lists ULB `24-02` and `21-05` wants one copy of ULB, not two. None of the three names a repository: the WA-Catalog convention (`<host>/WA-Catalog/<language>_<resource>`, `catalogueUrl`) is the one place that turns a reference into a URL, and `normaliseRepoUrl` is how two URLs are compared (case-folded, no `.git`, no trailing slash — Gitea answers `wa-catalog` and `WA-Catalog` alike).

Sefer WRITES relationships the way WA's own tools do (`Tech_Advance/leb-x-bisa_reg`, commit `7bd978c`): the authority `wycliffeassociates` (`https://www.wycliffeassociates.org`), the id `wycliffeassociates::<language>/<resource>`, and `revision` holding the LISTED version (`"21-05"`), one relationship per listed version — not a commit (Will, 2026-10-06). The commit a copy holds is this device's fact, on the Library row. The code says "relationship" or "related resource" because Source is taken (the editable text of a Book); "source" appears only as the formats' own literals and in product copy ("Source texts").

`writeMetadata.ts` is the one place that writes a new project's description, from one form into both files: `metadata.json` (checked against `decodeBurritoMetadata` before it is returned, so a project Sefer writes is one it can open) and `manifest.yaml` (output only, for the organisation's other tools; the Burrito wins if they drift). Both follow what WA's converter wrote for `Tech_Advance/bwc_reg`, with contributors de-duplicated on a normalised key (`_` as a space, case-folded; a team written as one string stays one entry) and sources de-duplicated. The Writer migration is its first caller.

## Checksums

A Burrito ingredient carries the md5 and the size of the file it names, which
means every save of a book makes `metadata.json` wrong about that book.
`src/core/resources/checksum.ts` is what makes it right again, and it holds an
md5 of Sefer's own: Web Crypto deliberately does not implement md5 — it is
broken as a security primitive and the browsers will not grow it — and core may
not import `node:crypto`. Burrito uses md5 as a content FINGERPRINT, not as a
signature, so the weakness is not ours to fix; we only have to produce the same
digits every other Burrito reader produces. RFC 1321 is sixty lines of
arithmetic, and a package for it would be a supply-chain surface for nothing.

`refreshIngredientChecksums(metadata, readBytes, names?)` is the policy: it
recomputes the named ingredients (every one by default) through a reader the
caller supplies, leaves an ingredient whose bytes it cannot read exactly as it
is — a missing file is a fact about the project, not a reason to invent a
checksum — and reports which rows moved, so nothing is written when nothing
changed.

Where it is called: `ProjectAdmin.refreshChecksums(root, names?)` wraps it over
the `FileSystem` port and writes through the same schema gate as every other
metadata edit, and composition hangs that off `SaveCoordinatorOptions.onSaved`
(`src/app/services.ts`). Save must not know what a burrito is and ProjectAdmin
must not know when a save happened, so the two meet in composition;
`ingredientFor(fileSystem, path)` answers which project a written path belongs
to and what the ingredient is called inside it, by walking up at most four
levels to the nearest `metadata.json`. A path under none is a folder of loose
USFM, and nothing happens.

## Import and Library

Two modules sit on top of those schemas. Neither redefines what a Burrito or a Resource Container is; both decide things _about_ a folder of files, through the `effect/FileSystem` port only.

`src/core/resources/import.ts` is the three-step path from foreign bytes to a project, and the steps are separate so that nothing unvalidated ever lands in a project.

- `stage(fileSystem, paths, stagingRoot)` copies what the user picked into a fresh `<stagingRoot>/<stageId>/`. A picked directory contributes its _contents_, so a Resource Container folder puts `manifest.yaml` at the staging root; a picked file contributes itself. The staging directory comes from the port's `makeTempDirectory`, which is how core gets a fresh name without owning a source of randomness.
- `classify(fileSystem, { root })` answers `burrito | resourceContainer | looseUsfm | unknown` and never fails: an unreadable or undecodable candidate simply is not that kind. A `metadata.json` that decodes as Burrito is a Burrito; a `manifest.json` or `manifest.yaml` that decodes as a Resource Container manifest is one (the YAML is parsed by `readResourceContainerManifest`, the same reader the Library describes a root with; it used to be sniffed for `dublin_core:`). Otherwise, any `.usfm` file under the root makes it `looseUsfm`, and nothing makes it `unknown`. The Library calls the same function, so classification lives in one place.
- `commit(fileSystem, staged, { root }, via)` validates every staged `.usfm` file through `decode` from `packages/text/src/source.ts`, records provenance, copies the staged files into the project and removes the staging directory — a move. It refuses before writing: `Unclassified` when the staging directory is not one of the three kinds or holds no book, `InvalidBook` when a book is not canonical UTF-8 text. Provenance is a JSON list at `<root>/.sefer/provenance.json`, written with `writeFileAtomic`, one record per import, appended through `appendArrival` (`src/core/project/provenance.ts`): `via` (`zip` or `folder`), `stageId`, the source paths, the classification, an ISO timestamp and the committed book paths. It records **no content hash** — text identity is the engine's xxh3 at the Galley boundary, never core's.

`src/core/resources/library.ts` is the registry, and it keeps the vision's two independent facts apart (§15.2): a resource's semantic _kind_ is what it is, its _role_ in a project is what it is for.

- `Resource { id; container; content; format; root; title; abbreviation?; language?; languageName?; subject?; identifier?; version?; upstream? }`. The id is the root path: a resource is where it lives, and nothing in core mints identifiers. `abbreviation` is the text's shorthand for a control too narrow for its title (`ULB`): a Resource Container's `dublin_core` identifier, a Burrito's `identification.abbreviation` localized like its name. It is never the `identifier`, which for a Burrito is its primary id, a GUID, and stays what recognition and `answers` compare. A row stored before it existed has none until the root is added again, and shows its title. `languageName` is the language's name as the metadata gives it, kept for a tag the browser's `Intl.DisplayNames` cannot name (`nxi`, from a Writer project), and stored like `abbreviation`; the reference panel also names such a tag from the reader's projects' metadata and the catalogue's rows. `container` is how it is packed (`ContainerKind`), and a `library.json` that still says `kind` reads as the same fact; `content` and `format` are what it holds and which reader parses it, from `recognize` (below). `add` refuses `Unsupported` for a kind or format Sefer has no reader for, and a row written before kinds is recognised again from its own metadata on load. `add(root, upstream?)` classifies through `classify` and describes the root through the same `readProjectMetadata` a project's header uses, so a Resource Container's `manifest.yaml` names it; the folder name is the title for loose USFM. `upstream { url, commit }` is where a cloned copy came from, stored normalised; `cloned(url)` finds a copy by it, which is what makes a second pull of the same text none.
- `declare(projectId, related)` is told, when a project opens, what that project declares as its source texts. It is held for the session.
- `pick(projectRoot, role, resourceId)` adds a resource to the set the project shows under `role`; `unpick` removes one; `resolve(projectRoot, role)` returns every resource picked for the role in pick order — and for `source` with nothing bound, the held copies of what the project declares (a copy cloned from `WA-Catalog/<language>_<resource>`, or one declaring that language and identifier) — and `picked(projectRoot)` returns all of a project's picks so a shell can lay out panes without knowing the roles up front. `Role` names the well-known roles (`source`, `notes`, `reference`, `glossary`; `ROLES` also spells `tn`, `tw`, `tq`) and stays an open string, so a project can bind a role Sefer has no surface for yet. A role holds many resources on purpose — two source texts side by side is ordinary. Apart from that declared default, an empty result is explicit, never substituted. The same resource can be a source in one project and a reference in another; binding changes nothing about the resource. Each resource also carries `subject` — the Burrito flavor or the Resource Container subject — so a surface can choose a renderer.
- `readBook(resourceId, bookId)` returns `Option<string>` — the WHOLE canonical text of that resource's file for the book, decoded the one way `packages/text/src/source.ts` decodes anything. It finds the book file as the first `.usfm` path whose name contains the book code, and then stops: no slicing, no interpretation. It exists because Galley parses a **book**, not a fragment, so a surface that wants the reference painted the way the editor paints the project cannot be fed a sliced passage. `none` when the resource is not registered or has no file for that book — a reference Bible that simply lacks Philemon is the ordinary case, not an error.
- There is no door that answers one verse. The Library used to slice a passage out with a `\c`/`\v` regex; Sefer never reads a designator itself, so a caller that wants a verse reads the book and asks the engine. Key terms' `sourceReadings` does exactly that: `readBook`, `galley.analyze`, `resolve` over the TOC, then the text from the verse label's end (`TocVerse.labelEnd`) to the verse's end.
- The registry is `<libraryRoot>/library.json` — the resource list (and, until each project is next read, the picks an older build kept there as `bindings`) — decoded through its own Effect Schema, held in memory for the life of the Layer and rewritten with `writeFileAtomic` on each mutation. A registry that does not decode is not a reason to refuse to start: the library comes up empty, says `library.load declined` in telemetry, and the resources are still on disk to add again. `LibraryLive({ libraryRoot })` is a `Layer<Library, never, FileSystem>`.

## Resource kinds

What a resource HOLDS is a closed union, `ContentKind = usfm | tn | tq | tw | macula-greek | macula-hebrew` (`src/core/resources/kinds/content.ts`), consulted in exactly two places: `recognize`, when the Library registers a root, and the renderer registry (`src/app/ui/kinds/registry.tsx`), when a screen draws it. Between them nothing narrows it; a pane, a workflow or Find asks whether a handle has a SLOT. The plan and the reasoning: `planning/items/2026-10-06-resource-kinds.mdx` (§3, §14, §15). To add a kind, a format or a container: [adding a resource kind](resource-kinds.md).

- **`recognize`** reads decoded metadata only — a Resource Container's `dublin_core` `type`, `identifier` and `format` (`ProjectMetadata.declared`), a Burrito's flavour — and answers a kind and its ONE reader (`Recognition`: `usfm`/`usfm`, `tn`/`rcHelpMarkdown`), or refuses with a sentence. Never a filename, never a content file, never a cascade of readers. An RC with no `type` (or `book`, `bundle`) is scripture, as every RC was before kinds; `tn` in a format with no reader (unfoldingWord's TSV), `tq`, `tw` and unknown types are refused.
- **`ResourceHandle<Entry>`** (`kinds/handle.ts`) is what an open resource can do: `places` (`at(address, context)` → its entries at an Address; `of(entry)` → an entry's Addresses), `documents` (the haystack for Find's default text find), `edit` (typed, filled by no kind: read-only is its absence), `info`, `release`. Every call is an Effect failing `Unavailable` (`Missing`, `Unreadable`, `Unsupported`). Tier 2: Address is the only vocabulary; nothing in it is USFM. `PlaceContext.versesIn` lends the open project's verse counts to a layout that leaves a range open — a stand-in for a resource's own versification.
- **The kind table** (`src/app/kinds/table.ts`) is a record over `ContentKind`: the role a pick takes (`tn` for notes), whether its files are USFM books for the engine (`holdsEngineBooks`, which `workflows/references.ts` asks instead of a file extension), how it is packed where its tree is too many files (`pack`), and how a handle opens. In `src/app` because a row may point at a core adapter or a platform one (Macula's wasm). `shell.resources` opens each handle once and releases them with the project.

### Translation Notes

WA's `en_tn` (`type: help`, `text/markdown`) is chapter directories of chunk files. `kinds/tn/rcHelpMarkdown.ts` is its reader, pure: each file is split at its top-level `#` headings as markdown-it finds them (html off), the cut made in the original text so a file's notes concatenate back to it; text before the first heading is a note with no quote; `NN/index.md`, `title.md` and names the layout does not have are listed in the pack's `skipped`; two files claiming one place refuse the book. **Convention, not spec,** and named so in `closeAtNextSibling`: a chunk's number is its first verse and its range closes at the next sibling; the last chunk runs to the chapter's end, which only a verse count can close. `note.ts` turns a record into a `Note { address, openEnded?, ordinal, body, quote?, heading? }` — `openEnded` when no count was lent — and decides which notes answer a place: the chunks covering a verse; a chapter's introduction at its head; the book's at `intro`.

The on-disk layout stays upstream's; what Sefer reads is a derived per-book pack, `<root>/.sefer/packs/tn/<BOOK>.json` (`kinds/tn/pack.ts`). Where the raw tree is present (desktop's clone, a picked folder) a pack is stamped with a fingerprint of its book directory's listing and rebuilt when that moves, so a pull invalidates exactly the books it touched; `.sefer/` is in a clone's git exclude. Where it is not — the Web — the packs ARE the resource: `arrival.referenceCopy` clones newest-only into the memory FileSystem, `recognizeRoot` reads its manifest, the kind's `pack` step (`packHelp`, reading through an `UpstreamTree`, `kinds/tree.ts`) writes one pack per book plus `manifest.yaml`, `LICENSE.md`, `README.md`, checks each pack reads back whole (same book, same number of notes; the full schema decode every later read makes was most of the step's time), and only then is the root added to the Library; a failure removes what was written. On desktop `referenceCopy` is an ordinary clone into the Library's folder, then indexed at once by the kind's `index` step (`indexHelp`: every book's tree-stamped pack built in place, with the same "Packing PSA: book 19 of 66" progress the Web shows), so neither a book's first read nor a first search over a Bible is the moment its pack is built; a failed index does not fail the download, because a read rebuilds. Where the host provides `FolderTree` (desktop, `kinds/tree.ts`) a book's listing for the freshness check, and its files for a build, are one call each instead of one per file; the handle captures it at open, as it captures its `FileSystem`, because the notes pane forks its reads outside the services runtime. Measured with the display awake (2026-10-13): Psalms' notes 1.3 s on first read and 0.25 s from a pack, where they were 39.8 s and 12.3 s; en_tn's download 29 s and its indexing about four minutes; the Bisa Bible's first notes search 2–3 s, where it was about seven minutes. The handle (`kinds/tn/adapter.ts`) holds three books' packs and loads others on demand.

Translation Notes are offered in one place: the reference column's menu, under **Reference material**, in a section headed **Translation Notes** — one row per language, "English (en)" with the language's own name below it (drawn in its `direction`), and a download icon that turns to a spinner while that one downloads. The rows are the Language API's (`listTranslationNotes`, `src/app/catalogue.ts`), read the first time the menu opens, decoded through an Effect Schema, A–Z by English name. They come from the PRODUCTION API (`TRANSLATION_NOTES_API`) on every channel, whatever catalogue the build is configured for: the one hard-wired host in that file, by Will's ruling (2026-10-15), because the dev API lists no English notes. Above them, each copy already held in the Library's folder is listed with **Remove** (`removeHelp`, `src/app/kinds/download.ts`: the Library forgets it, its folder goes, a toast says so; no confirm, and downloading again is the undo; the menu stays open so the row is seen to move back). A row is left out when its URL is held, or when notes in its language are held, so a device with `WycliffeAssociates/en_tn` is not offered `WA-Catalog/en_tn` as a second English (their book folders are the same git trees, probed 2026-10-15). The query:

```graphql
{
  content(where: { resource_type: { _eq: "tn" }, git_repo: { username: { _eq: "WA-Catalog" } } }) {
    language {
      ietf_code
      english_name
      national_name
      direction
    }
    git_repo {
      username
      repo_name
      repo_url
    }
  }
}
```

`repo_url` names its own host, as a share link does, so whichever cloud the build is configured for the notes come from where WA publishes them. Probed 2026-10-15: 34 languages on the production API (English is `WA-Catalog/en_tn`), 33 on the dev API (no English). While the list is read the section says so; a failed read says "offline" (the request never reached the API) or "could not read", and the next open of the menu asks again. A build with no catalogue URL still lists notes, since the list does not use it. Only TN: no other help kind is listed until the PO asks for it (2026-10-15). The projects page lists no notes ([landing](landing.md)). Every row downloads through `downloadHelp` (`src/app/kinds/download.ts`), which joins a download already running for the same repository rather than starting a second into the same folder: one `import.remote` operation and one progress toast that moves the whole way — the megabytes received (the Web transport counts the pack as it arrives, since git reports nothing between "Compressing objects" and the end of the download), then reading, then "Packing ROM: book 45 of 66" — and ends saying what happened. On slow 3G (400 kbit/s) en_tn took 176 s and the toast moved every 5 s throughout. Picked, the column draws it through the registry as `NotesPane`: the notes for `shell.place()`, each its own block, consumed through `createHeld` so the last verse's notes stay while the next load.

### Provenance and updates

Every copy of reference material records where it came from and which version it holds, so an update check needs nothing new on disk. **The check itself is not built.** This is one case of the one upstream pattern for anything from a git remote (record `{ url, commit }`, probe the head, compare, offer), stated once in [sync](sync.md), "Upstreams: one pattern for everything from a git remote", with where integrating it belongs.

**What is recorded, and where:**

| Fact                           | Where                                                                                                                                                                        | Written by                                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| The upstream URL and commit    | `Resource.upstream { url, commit }` in `<libraryRoot>/library.json` (the URL stored normalised)                                                                              | `arrival.referenceCopy`: after the newest-only clone it resolves `HEAD` and calls `Library.add(into, { url, commit })`, both hosts |
| The commit each pack came from | the pack's stamp, `{ kind: "import", at, commit }`, in every `<root>/.sefer/packs/tn/<BOOK>.json`                                                                            | `packHelp`, on the Web, where the packs ARE the resource                                                                           |
| What the copy holds            | the copy's own `.git` (desktop: an ordinary clone, `HEAD` is the commit) and its listing fingerprint in each pack stamp, `{ kind: "tree", fingerprint }`                     | the clone; `indexHelp` when it arrives (desktop), `bookPack` when a book's listing has moved                                       |
| The arrival                    | `<root>/.sefer/provenance.json` (desktop only: on the Web the clone is staged in memory and this record is dropped with it; the Library row carries the same URL and commit) | `cloneRepository`                                                                                                                  |

`Resource.upstream` is the same generic pattern every Library copy uses (a gateway source text records it the same way, and `Library.cloned(url)` finds a copy by it, which is what makes a second download none). It is per device: a project never names a copy by URL.

**How an update check would work:**

1. **Ask.** `Remote.probe(upstream.url)`: the server's refs in one round trip, no transfer. If `head` equals `upstream.commit`, nothing is new. This is the question the shared project's check asks first (`checkForChanges`, [sync](sync.md), "Checking on open, and sending on save") and the one the Writer upstream check asks for each `.upstreams.json` row (same chapter, "Writer projects a project follows").
2. **Say.** "Translation Notes have changed upstream": wherever the copy is picked (the `/projects` Notes section it once named is gone). Nothing moves without the person.
3. **Bring it in.**
   - **Web:** `referenceCopy` again, into a fresh folder beside the old one: clone newest-only into memory, `packHelp` writes every book's pack (about 13 s for `en_tn` in all, of which packing is under 4 s, so re-packing only the changed books from the clone's own diff, `Git.changedPathsBetween`, would save little), `Library.add` with the new commit, then the old folder is removed. A failure leaves the old copy as it was.
   - **Desktop:** a fast-forward pull in the copy itself. Nobody edits a reference copy, so it never conflicts. The pull changes files in the chapter directories, each book's listing fingerprint moves, and `bookPack` rebuilds exactly the books the pull touched the next time each is read. Then `Library.add(root, { url, commit: newHead })` records the new commit.
4. **Release.** An open handle on the old copy is released (`shell.resources`), so panes reopen on the new packs.

**Why a pull never fights the packs:** the on-disk layout is upstream's, untouched: the chapter directories of chunk files a `git pull` updates. What Sefer derived from it lives only in `.sefer/packs/`, which is in the clone's git exclude, is never committed, and is rebuilt from the files whenever they move. There is no restructured copy of upstream's content for a pull to conflict with. On the Web there is no working tree at all, so "pull" is "download again and re-pack", and the stamped commit is how the copy says which upstream version its packs describe.

**How it differs from the two upstream checks that exist:** the shared project's check (`syncActions.checkForChanges`) and the Writer upstream check (`writerWatch.ts`, `.upstreams.json`) both concern a project's TEXT, which is merged or reviewed, never overwritten. A reference copy is read-only and nobody's work, so its update is a replacement, not a merge, and needs no Review. `.upstreams.json` is committed in a project because teammates follow the same Writer projects; a reference copy's upstream is this device's fact, in `library.json`.

## Binding a reference, and where the binding lives

The Library had no surface, which made "how is a reference Bible supposed to work?" a fair question: the port could bind, and nothing could call it. The reference column
(`src/app/ui/workspace/ReferenceColumn.tsx`) is that surface, and it is the only one.

The column shows ONE text, straight on the page — a reference pane drawn bare (`ReferencePane bare`: no card, no paper, no title line, only its Follow toggle) — under a **Reference language** menu that says whose text it is ("English (en)"). The editor's crumb strip shuts the whole column (`workspace.referenceOpen`, "Collapse the reference text"), and nothing else does: a second button on the column that folded it to a stack of cards was one close too many (Will, 2026-10-22).

The menu lists, in order:

1. **What is on this device**: the texts this project picked or declares, then the Library's own copies, scripture before helps (the PO's words, **Source texts** and **Reference material**; the kind table decides). Choosing one shows it, picking it for the project first under its kind's role (`Library.pick(projectRoot, roleFor(resource), id)`: `source` for scripture, `tn` for notes) if it is not already shown, and draws it through the renderer registry (`ResourcePane`).
2. **Reference material**, folded: one list at a time, under a segmented toggle — **Translation Notes**, **Bibles**, **Your projects** — with a search box (language name, its own name, or code) pinned above the list (Will, 2026-10-22). It opens on Bibles when no Bible is on this device, else on Translation Notes.
   - **Translation Notes**: the notes on this device, each with Remove, then WA-Catalog's `tn` repositories the Language API lists (`listTranslationNotes` in `src/app/catalogue.ts`), one per language.
   - **Bibles**: WA-Catalog's `ulb` repositories in the official gateway languages (`listSourceTexts`: `resource_type: ulb`, owner `WA-Catalog`, `wa_language_metadata.is_gateway`), with no copy here. Nothing else: the PO ruled (2026-10-22) that a source text is a real WA Catalog ULB in an official gateway language, not one of the dozen other English ULBs a language search turns up, and never the UDB. The catalogue types a few non-ULB texts as `ulb` where a gateway language has no ULB (Persian's OPV and NMV, Burmese's JUDS); those are kept and named by their repository ("Persian (Farsi) (fa) · OPV"). For a project that declares no source text, English comes first. Choosing one downloads it through `sourceTextCopy` in `src/app/arrival.ts` — the held copy if there is one, else a clone into the Library's folder — under an `import.remote` operation (`import.source: reference`), then picks it.
   - **Your projects**: every project on this device except the open one, from the index the landing screen uses (`listProjects`). A neighbouring heart language reads well beside a translation (Will, 2026-10-08). Choosing one calls `Library.add(root)` (idempotent) and then picks it.

With nothing picked, the column shows what the project DECLARES (`Library.resolve` falls back to it), so there is no "default given once" to remember: choosing another text replaces it, and removing one is not a thing the panel does. A declared text that is not on this device is named, with **Download**, which pulls it through `arrival.ts`. **Edit as your own project** — a full move into the projects folder (Will, 2026-10-06: once edited it is no longer WA's official text), after which projects that read it fall back to downloading the official one — is in Settings, "Source texts on this device" (`SourceTextsCard`), not on the pane: it is a rare, internal move.

The projects page lists gateway languages only with Settings → Advanced → "Show gateway languages on the projects page" (`projects.showGateways`, off by default). A gateway row downloaded there is still a source text and lands in the Library, never "Your projects".

**Where a copy lives.** Everything cloned FOR the Library — a WACS gateway row, a source text a project declares — goes into `<appData>/library/<owner>/<repo>`, outside the projects folder, so "Your projects" never lists it. `cloneArrival(services, "project" | "sourceText", url)` is the one switch: a project is written under `projectsRoot` and remembered in the index; a source text is written under `libraryRoot`, added to the Library with the commit it holds, and announced on `libraryRevision`. Every arrival of a project (download, clone, zip or folder import, Writer assembly) then pulls the source texts its metadata declares, each at most once per device, with one toast; a copy whose version is not the one listed says so ("listed 24-02; this copy is 24-07"). A failed source-text clone leaves no partial folder behind in the Library.

Where a pick lives: in the PROJECT, as `referencePicks` in its `.sefer/project.json` — this device's memory of that project ("on this project I usually read that source text"), read when it reopens, never committed, and written through the one merging writer (`src/core/project/projectState.ts`) that a rename also uses, so neither erases the other. Picks are keyed by the project's root; an older build kept them in `library.json` under `Project.id` (`root` or `root#<metadata id>`), and they move into the project the first time its picks are read. The same resource can still be a source in one project and a reference in another, and `×` is an UNPICK, never a delete.

## A reference is a read-only editor, not a card

A bound reference used to be a card holding one passage, sliced out of the USFM by a regex the Library no longer has, and stripped of its markers for display. It is now a **read-only `EditorView` over the whole book** (`src/app/ui/workspace/ReferencePane.tsx`, one per bound resource), and the change is not cosmetic. A card could not show markup, could not be scrolled, and painted verses by a rule of its own — so it could disagree with the editor two inches away about what the same text looks like. A pane is the same `decoField` over the same `DocStructure`, so the two sides cannot drift.

`packages/editor/src/recipes/reference.ts` is the mount. `mountReference({ parent, text, analyze, mode })` answers a `ReferenceMount` with `view`, `setMode`, `clipTo`, `showChapter`, `showPair`, `pairBlocks` and `destroy`. What it installs is the editor's READING half and nothing else:

- `analyzer` + `readingLayer` — structure, pick, projection, decorations. This is what makes the reference look like the editor.
- `viewLayer()` — line wrapping, the render window (a long reference is decorated a screenful at a time, like the editor), atomic ranges, bidi isolates.
- a mode **compartment** holding the same three things `BookEditor` reconfigures: `assignment.of(projectionFor(mode))`, `modeFacet`, and `EditorView.editorAttributes.of({ class: "cm-mode-<mode>" })`. The class rides the facet rather than the element because CodeMirror rewrites `view.dom`'s class attribute from its own facets.

What it deliberately does NOT install: the kernel phases, the command keymap, history, the linter. A rule that refuses an edit is dead weight over a document no transaction will ever change. Read-only is said twice — `EditorState.readOnly.of(true)` stops any command that asks, `EditorView.editable.of(false)` keeps the browser from composing into it — and selection still works, because a reference you cannot copy out of is not a reference.

It is **not** a satellite and not a window. Those borrow a `Funnel` and may write; a reference has no Book in this process at all, and the whole of its discipline is that nobody may edit it.

`borrowedStructure` is not used: the canonical parse describes the PROJECT's book, and this is a different text of the same book. Each pane takes its own `galley.memoize()` and parses once — the document never changes, so the memo answers every later read.

**Following the reader is by verse, and only when it helps.** The book page makes one aligned group (`createAlignedGroup`, `packages/editor/src/recipes/align.ts`) and provides it to the editor and every pane (`src/app/ui/workspace/aligned.ts`). A view that the READER scrolls — wheel, touch, a scrollbar drag, a key that scrolls — emits its anchor: the verse in its MIDDLE, where the reader's eye is (the next verse, when a heading is there), named by Location's `addressAt` over its own table of contents. The group moves every follower with `resolve` in the follower's table — the join Find uses to put a reference hit on the project's verse, so a bridge lands where it should — and in `reveal` mode only when that verse is outside the follower's middle band (20–75% of its height), bringing it to the middle (`revealInBand`, which the paired block uses too when the caret moves); `exact` keeps it at the same height. Both through CodeMirror's own `scrollIntoView`, which measures lines it had only estimated. A view the group moved had no input from the reader and does not lead, so nothing comes back; a jump the app makes on purpose (a chapter picked, a hit opened) announces itself with `lead`. The clip is still chapter-level: the pane clips to the same chapter number when the editor is clipped. Following is a per-pane toggle (`FollowToggle`, the chain in the pane header), seeded from the `editor.syncReferences` setting, and it decides both directions: a following pane leads the editor too. Review's Whole book uses the same group for its two panes, and the same strip the editor reads from — `LocationStrip` and `Crumbs` (`src/app/ui/workspace/Crumbs.tsx`), Book · Chapter over the books and chapters with changes, the chapter arrows, and the chain that links the two panes.

**Pairing is caret-driven.** `shell.caret()` is the main editor's caret, and `ReferencePane` finds the source's equivalent — the verse by sid, or the block when the caret is in a heading or front matter — and marks it with `showPair`; `pairBlocks` (the `editor.pairBlocks` setting) chooses whether whole blocks are paired.

A reference that has no file for the open book shows one line — "Unlocked Literal Bible has no Philemon" — instead of an empty editor.

The `×` in each pane's header still UNBINDS and does not delete.
